## Native architecture decision

1. Current approach: prove the supported NAS `createVMFromBackup` path in exact Apache CloudStack 4.22.1.1 before a custom DR controller.
2. Advantages: CloudStack retains accounts, RBAC, async jobs, allocation and storage lifecycle authority; fresh clones avoid conflating this path with in-place restore.
3. Disadvantages: both Zones and retained source/backup metadata must belong to one management database; metadata alone cannot prove repository reachability or restored contents.
4. Alternatives: a separate DR Management database with copied NAS files does not supply native backup metadata; two Basic Zones encounter the source constraint below; storage-native replication remains a later provider gate.
5. Recommendation: retain the existing Basic source if useful and use an Advanced recovery Zone with explicit account-owned recovery networks in DC's management database. DR `.20` may retain its separate lab console, but its KVM agent must not belong to two independent CloudStack deployments.
6. Reason: `UserVmManagerImpl.allocateVMFromBackup` populates network IDs from backup metadata when omitted; the Basic allocator rejects non-null network IDs. `iptonetworklist` is converted to the same network-ID list. An Advanced destination avoids a core patch.
7. Implementation impact: the acceptance adapter rejects Basic destinations before mutation, requires exact fixture ownership/Zone/network/repository/backup IDs, requests stopped clones, and journals mutation intent and returned job IDs durably.
8. Risks: wrong network/disk mapping, lost submission responses, stale fixtures, conflicting deployments, source-record purge and shared lab failure dependencies.
9. Mitigations: private locked journal; no blind mutation retry; explicit recorded-ID cleanup; original repository/offering linkage; separate expected and observed guest hashes; exact live-environment reservation; no source record purge.
10. Tests: fourteen mocked native API/journal cases, nine actual PowerShell API-collector tests including HTTP 401/431/redaction/array cases, ten DC collector tests, seven exact-VM console-wrapper tests. These are source tests, not live native recovery proof.
11. Rollback/recovery: native acceptance cleanup soft-deletes only completed, recorded stopped recovery clones after identity checks; it never deletes source VMs, backups or shared infrastructure. Lost/uncertain submissions require exact job reconciliation. UI deployment preflight failures above occurred before deployment began.
12. Production-readiness status: `PARTIAL` overall; native guest recovery, RPO/RTO, failover/failback and independent-site resilience are `NOT_TESTED`.
