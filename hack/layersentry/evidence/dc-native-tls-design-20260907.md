## Exact native design

CloudStack 4.22.1.1 source at combined product `dc58f76f67dac13aa886c8d45475944f31b0c039` retains independent HTTP and HTTPS connectors in `client/src/main/java/org/apache/cloudstack/ServerDaemon.java`. It reads `https.enable`, `https.port`, `https.keystore` and `https.keystore.password`; HTTP defaults remain enabled on8080. `utils/src/main/java/com/cloud/utils/server/ServerProperties.java` exposes the native port/keystore properties. The native service runs as `cloud`, so the installed keystore and password-bearing configuration require root:cloud0640, while private journal material is root-only. Existing configuration bytes and original owner/group/mode are retained; the candidate only appends explicit HTTPS8443 settings. Ambiguous Java Properties escaping/continuation, another HTTP port, disabled HTTP, an existing unowned HTTPS connector interactive password-decryption startup, or unsuitable bind/context path stops the plan rather than rewriting unrelated settings.

`ListCaCertificateCmd` constructs object name `cacertificates` and exposes the public certificate through `listcacertificateresponse.cacertificates.certificate`. `IssueCertificateCmd` is an Admin async API and returns the normal job reference first. `CertificateResponse` has object name `certificates`; the completed job carries `jobresult.certificates.certificate` and `cacertificates`. `RootCAProvider.generateCertificateUsingCsr` builds the signed certificate using the supplied CSR public key and returns `new Certificate(clientCertificate, null, ...)`; it does not create or return a private key. The implementation always supplies a locally generated CSR and rejects a response containing a private key. It never uses the API's no-CSR key generation path.

The exact `CertUtils.generateV3Certificate` leaf path includes SANs but no EKU restriction. The API description “client certificate” does not prove or disprove server usability: each returned leaf must pass real OpenSSL `verify -purpose sslserver` against the original CA with default CApath/CAstore disabled, exact IP10.10.10.14 and actual hostname SAN checks, plus certificate/CSR/private-key public-key equality. An unexpected issuer, CA rotation, extra/missing SAN, client-only EKU or key substitution fails. The original RootCA public certificate is pinned by DER SHA256 and retained on target; the CA private key is never requested, read or copied.

The selected mechanism reuses native CloudStack CA and Jetty rather than introducing another proxy/CA authority. A reverse proxy would add another service/configuration boundary and was not needed for this scoped prerequisite. A self-signed leaf would replace the existing trust authority; copying the management server's CA private key or requesting API-generated keys would widen secret exposure. XaaS does not apply to native management HTTPS. Exact source controls these contracts; the published 4.22 API docs identify themselves as4.22.0.0 and were only cross-checked, not substituted for4.22.1.1 source. This is a bounded lab prerequisite, not a production TLS/topology redesign or an upstream CloudStack change.

Official references: [issueCertificate API](https://cloudstack.apache.org/api/apidocs-4.22/apis/issueCertificate.html), [listCaCertificate API](https://cloudstack.apache.org/api/apidocs-4.22/apis/listCaCertificate.html), [OpenSSL3.2 verification options](https://docs.openssl.org/3.2/man1/openssl-verification-options/), [JDK17 keytool password-file/import/export options](https://docs.oracle.com/en/java/javase/17/docs/specs/man/keytool.html). Exact local source files above plus `server/src/main/java/com/cloud/api/response/ApiResponseSerializer.java` and `plugins/ca/root-ca/src/main/java/org/apache/cloudstack/ca/provider/RootCAProvider.java` determine serialization and CSR behavior. No unrelated open-issue/community architecture survey was used to infer current target health; real Plan/runtime evidence remains required.
