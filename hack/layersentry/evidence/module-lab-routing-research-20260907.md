# DC/DR and Kubernetes lab routing discovery

The existing Basic source Zone uses Guest traffic for the SystemVM default route. Current evidence establishes the guest bridge and Windows gateway address but does not establish routing from the guest subnet to required DNS, NTP, template and management endpoints. Native CloudStack SystemVM routing remains authoritative; no guest image or CloudStack core rewrite is proposed.

[Microsoft's Hyper-V NAT documentation](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/setup-nat-network), reviewed 2026-09-07, documents a single WinNAT internal prefix and sharing it across internal switches with coordinated disjoint address allocation. Thus another independent WinNAT instance is not a supported fix. A covering prefix, an external routed network, or a separate lab router are alternatives; none is selected for mutation until actual host routes, NAT mappings, HNS networks, existing endpoint assignments and conflicts are checked. Enlarging a prefix alone is not proof of guest egress, return traffic, DNS or Kubernetes API load-balancer reachability.

The new manual collector is read-only, requires exact TESTSER switch identities, projects only public network fields, and distinguishes an unavailable HNS query from an empty result. It preserves existing networking and collects the prerequisites for a concrete network design. Parsing is a source check; the Windows runner receipt is the next verification gate. No rollback is applicable because discovery performs no infrastructure mutations. This is lab automation only, with no upstream package, CloudStack-core, API, or tenant-lifecycle change. Production status remains NOT_TESTED.
