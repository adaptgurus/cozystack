# Two Rocky Linux VM functional lab

Status: `PARTIAL`. The helper implements guarded Hyper-V phases; Windows parser/mocked tests and live resize/boot evidence must pass for the exact commit before runtime claims. Two guests on one physical Hyper-V host support functional cross-Zone exercises and share the host, storage and network failure domains. Rocky, KVM and CloudStack acceptance remains separate from Hyper-V start/heartbeat checks.

## Decision

Use an existing Rocky guest resized to 12 vCPU and 40 GiB static memory, plus a second fresh Rocky guest with 16 vCPU and 40 GiB static memory. This reserves at least 16 GiB for the host based on measured physical and available memory. Other VMs' full memory reservations are included. The CPU ceiling is two allocated vCPUs per host logical processor; the second guest requires at least 16 host logical processors. This is a functional-lab policy, not a production sizing recommendation.

The previous three-node Harvester helper force-stops/reuses VMs and accepts sparse-disk capacity risk. It is unsuitable for preserving the existing CloudStack guest. This helper changes no existing disks, switch, NAT, IP, firmware or guest configuration. A fresh Gen2 ISO install prevents copied CloudStack databases, host identity, machine IDs and SSH host keys. VHD imports are rejected until an image generalization and independent-identity verification pipeline exists. The trade-off is an operator/installer step for the second OS. The second VM receives a fresh dynamic 100 GiB OS VHDX at SCSI 0:0 and a separate fresh dynamic 500 GiB data VHDX at SCSI 0:1. Both disk paths must be absent before either is created. No guest partitioning, formatting or Rocky installation is performed by this helper.

## Activation

1. Fetch integration HEAD and inspect current runner jobs. Drain any live mutation jobs and keep the runner external to the guest being resized. The new workflow serializes its own phases and takes a host file lock; historical workflows use other concurrency groups and do not honor this lock.
2. Obtain exact Hyper-V VM and switch GUIDs from current read-only inventory. Review guest CloudStack/libvirt workload state and gracefully stop or evacuate any nested workloads before authorizing resize. Save a DB/config backup and verify console access. Existing checkpoints block this helper; it never removes them or creates an implicit application-consistency checkpoint.
3. Copy `two-vm-lab-requests/example-resize.json` to a new request filename, fill the host and GUIDs, and commit the reviewed request. Empty ISO/path fields are required for `resize-only`. Do not include credentials. Names alone are not target authority.
4. Dispatch `.github/workflows/layersentry-two-vm-lab.yml` at the reviewed integration commit with `request=hack/layersentry/two-vm-lab-requests/<request>.json`, `phase=Preflight`, and no authorization. The workflow may need to be registered on the repository default branch before GitHub accepts dispatch. Preflight writes only evidence and a protected host journal; it makes no VM changes.
5. Review the preflight artifact and exact original CPU, memory, NIC and disk settings. Dispatch the same committed request with `phase=Resize`, `authorization=<requestId>:Resize`. It rechecks capacity and compares the original settings, gracefully shuts down the target, sets 12 vCPU/40 GiB static memory and nested virtualization/MAC spoofing, verifies disks/NIC and settings, and starts it if originally running. Hyper-V heartbeat must return; CloudStack/API/SSH/services must then be verified through the existing Rocky acceptance workflow.
6. For a second guest after the existing guest has already been resized, prepare a new `create-only` request using `two-vm-lab-requests/example-create.json`, the publisher-verified Rocky 9 ISO path and SHA-256, and a nonexistent dedicated VM root such as `C:\LayerSentry\dr-lab`. Dispatch Preflight, then Create and Start individually with matching authorization tokens. Create-only Preflight verifies the existing 12-vCPU/40-GiB guest, nested virtualization and MAC spoofing, and records `ReadyToCreate`. It requires no repeat Resize and never stops or reconfigures the existing guest, including during Rollback. The older `two-vm` mode still requires Preflight then Resize before Create. Create leaves the new guest off. Start verifies second-VM compute, switch, disk attachments/types/sizes and ISO identity, rechecks total host reservations and disk headroom, then boots the installer and reports OS installation `PENDING`. Configure a unique guest hostname, static IP, machine identity and SSH host keys through fresh installation; compare both guests before CloudStack registration.

The second-VM plan requires destination free space for the entire new 600 GiB disk allocation, growth of existing attached VHDs on that volume, and 20 GiB spare. Dynamic allocation reduces immediate disk consumption but does not relax this full-growth gate. Start rechecks that gate because unrelated workloads may consume space between phases. ISO digest validation is integrity checking against the reviewed operator digest, not independent proof of publisher authenticity. Check the Rocky publisher signature/checksum before selecting that digest. Reparse points, wildcard/traversal paths, UNC media, existing destination directories, checkpoint chains and ambiguous VM states fail closed.

### Discovering the operator-provided ISO

Dispatch `phase=DiscoverMedia` with an existing reviewed request bound to the correct host and no authorization token. This phase reads only `<system drive>:\Users\<profile>\Downloads\Rocky-9.8-x86_64-minimal.iso`; it performs no recursive whole-disk search and makes no VM or journal changes. It skips reparse profile directories and rejects reparse Downloads/media paths, remote roots, zero matches or multiple matches. The result artifact supplies `media.isoPath`, `media.isoSha256` and `media.sizeBytes` as exact candidate request values, with `publisherVerification=PENDING`. A filename alone does not establish publisher origin. Independently compare the discovered digest with the official Rocky release checksum and verify its publisher signature before committing an activation request. No ISO path or digest is assumed by the example request; all placeholder values must be replaced and reviewed. DiscoverMedia does not authorize Create or Start.

## Recovery and failure behavior

Host journals live under `%ProgramData%\LayerSentry\two-vm-lab`, restricted to SYSTEM and administrators and bound to the request bytes and host. Preserve the exact request and journal across checkout/runner cleanup. Resize/Create/Start intentions are journaled before mutation, so interrupted operations do not silently restart creation. Raw guest content, credentials and exception bodies are not uploaded in evidence.

For a failure after resize, dispatch the same request with `phase=Rollback`, `authorization=<requestId>:Rollback`. The second guest, if owned by the journal, is gracefully stopped and retained with autostart disabled; both its OS and data disks are retained, including partially created disks. For resize-enabled requests, the original CPU, memory mode/range, virtualization and NIC spoofing settings are restored; the original running/off state is restored subject to measured memory availability. Create-only rollback never stops or modifies the existing guest. Recovery of a resized guest retains the originally measured free host memory (capped at 16 GiB); forward starts always retain 16 GiB. No VM or disk is deleted. If the ISO installer cannot shut down gracefully, use console shutdown first; there is no forced power-off fallback. If the host crashes between New-VM and journaled ownership, inspect the orphan and retain its disks before recovery. If the original allocation no longer fits available memory, recovery stops with the guest off and requires restoring host capacity. This is configuration rollback, not database/data rollback.

## Validation

Run `powershell -NoProfile -File hack/layersentry/test-two-vm-lab.ps1` on Windows. The tests parse the scripts and exercise request rejection, identity-clone prevention, path constraints, memory/CPU/disk headroom, repeated graceful stop, heartbeat start, low-memory refusal and unstable-state refusal with mocked cmdlets. Additional tests execute fresh two-disk creation and reject existing data disks before any disk write; verify compute/network/disk drift refusal before Start; reject post-Create storage and reservation exhaustion; and verify exact media discovery, missing/duplicate matches, reparse media and remote-root refusal. The dispatch workflow runs these on a hosted Windows runner before acquiring the Hyper-V runner. Live crash/recovery injection, guest service checks, nested KVM usability, network reachability, backup/restore and DR remain `NOT_TESTED` until evidence is collected.

Microsoft documents [graceful Stop-VM behavior](https://learn.microsoft.com/en-us/powershell/module/hyper-v/stop-vm) and [nested virtualization configuration](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/enable-nested-virtualization). LayerSentry additionally verifies KVM inside Rocky; Hyper-V configuration alone does not establish that acceptance.
